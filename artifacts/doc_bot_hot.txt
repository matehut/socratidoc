1. COMO O BOT FUNCIONA
================================================================================

1.1 Visão geral
---------------
Bit é um bot Telegram de produção numa VPS. O processo do bot (handlers) fica
leve: valida acesso, rate-limit, grava estado pendente no Redis e responde já.
Trabalho pesado de rede (scan passivo, clone de site) vai para fila RQ + worker.

Arquitetura em camadas:

  Telegram (polling | webhook)
        │
        ▼
  app/bot/          handlers, menus, teclados  (zero I/O de scan)
        │
        ├─ app/services/   regras: URL, scan, tools locais, acesso, jobs
        ├─ app/adapters/   DB SQLite, Redis/RQ, httpx, sendMessage/sendDocument
        └─ app/core/       Settings, logging JSON, exceptions
                │
                ▼
             Redis ── fila RQ "scans"
                │
                ▼
  app/workers/      run_scan(job_id) / clone_job
                │
                ▼
             SQLite (users, jobs) + notificação ao chat via HTTP Telegram API


1.2 Processos em runtime
------------------------
- bot.service  → /root/bit/run.sh → python3 -m bit.bot → app.main
  Modo atual: TELEGRAM_MODE=polling (getUpdates).
  Importante: NÃO pode coexistir webhook ativo no mesmo token.

- worker      → python -m app.worker (RQ Worker na fila "scans")
  Consome jobs de scan e clone; notifica o chat com adapters.telegram.

- Redis       → redis://127.0.0.1:6379 (fila + pending state por chat)

- webhook.service (/opt/webhook) NÃO é o receiver do Telegram.
  É o Distiller Flask (grok-format / orchestrator) chamado pelo Bit via HTTP.


1.3 Entrypoints
---------------
- bot.py          bridge: carrega env/hermes, reexec no .venv, chama app.main
- app/main.py     Application PTB, regista handlers, set_my_commands, run_polling
- app/worker.py   Worker RQ
- app/cli.py      bridge para Hermes chamar tools Bit sem polling
- run.sh          arranque systemd do bot


1.4 Controlo de acesso
----------------------
app/services/access.py + Settings:

- ADMIN_USER_IDS / ALLOWED_USER_IDS / ALLOWED_CHAT_IDS (lista CSV de ints)
- BOT_PUBLIC=false → só IDs allowlist (ou admin)
- ensure_allowed() corre em quase todos os handlers via decorator @logged
- /exportar e /claude são restritos a admin/dono


1.5 Configuração (app/core/config.py + .env)
--------------------------------------------
Principais variáveis:
  TELEGRAM_BOT_TOKEN / BOT_TOKEN
  TELEGRAM_MODE=polling|webhook
  WEBHOOK_URL / WEBHOOK_LISTEN / WEBHOOK_PORT / WEBHOOK_SECRET
  REDIS_URL, DATABASE_URL (sqlite:///./data/bot.db)
  BIT_ALLOW_NETWORK, ALLOW_PRIVATE_TARGETS, ALLOW_NONSTANDARD_PORTS
  RATE_LIMIT_USER_PER_HOUR, RATE_LIMIT_TARGET_COOLDOWN_SEC
  GROK_WEBHOOK_URL, GROK_WEBHOOK_SECRET, ORCHESTRATOR_WEBHOOK_URL
  RQ_QUEUE_NAME=scans


1.6 Persistência e estado
-------------------------
- SQLite (SQLAlchemy): users, jobs (status queued/running/done/failed)
- Redis:
  - fila RQ
  - pending por chat_id (tool à espera de params; TTL)
  - rate limit / flags auxiliares
- Logs JSON: request_id, user_id, command, job_id, duration_ms, status, error_type
  Token NUNCA é logado (redação).


1.7 Scan passivo (fila)
-----------------------
Slugs que enfileiram o mesmo worker de scan:
  analise_site, busca_viabilidade, pentest_etico, teste_api, rastrear_ip, scan

Fluxo:
  1) Handler valida URL (http/https, anti-SSRF) + rate limit
  2) jobs.enqueue_scan → DB job + RQ enqueue_scan_job(job_id)
  3) Resposta imediata com job_id
  4) Worker run_scan(job_id): DNS + TLS + HEAD/GET → format_scan_report
  5) send_message(chat_id, summary)

Clone (/clone) segue padrão semelhante com clone_job e timeout maior.


1.8 Tools locais vs stubs
-------------------------
app/services/local_tools.run_local(slug, params):
  - executa localmente: matemática, hash, conversor, senha, algumas respostas
    estáticas/educativas (tool_answers), etc.
  - slugs de SCAN_SLUGS são desviados para a fila
  - teste_firewall recusa port scan de propósito
  - muitas tools de texto/código respondem com guias/templates (não LLM embutido
    no processo do bot, salvo integrações Hermes/Claude/webhook)


1.9 Integrações externas
------------------------
- /hermes     → CLI Hermes Agent (subprocess), sem segundo poller no mesmo token
- /claude     → Claude Code bridge (dono)
- /webhook    → Distiller local (POST grok-format / site→JSX|HTML)
- Lovable/Bolt scanner defensivo (headers/fingerprints públicos)
- /tv         → CVEs públicas via NVD (relatório TXT)
- /cam_scan   → varredura IP camera (RTSP/HTTP) — só alvos autorizados
- /cam_snap   → captura frame (OpenCV se disponível)
- PDF context → pypdf/pdfplumber; documento vira contexto do chat


1.10 Conflito operacional crítico
---------------------------------
Um único token Telegram = um único consumidor de updates.
Se setWebhook estiver ativo, polling (getUpdates) falha com Conflict e o bot
fica "vivo" no systemd mas surdo. Correção: deleteWebhook + TELEGRAM_MODE=polling.
Hermes gateway no mesmo token deve ficar desligado quando Bit faz polling
(scripts/sync_all_telegram.py documenta isto).

4. FLUXO DE MENSAGENS
================================================================================

4.1 Diagrama (polling)
----------------------

  Utilizador Telegram
        │  mensagem / callback / documento / foto
        ▼
  Telegram API
        │  getUpdates (long poll)
        ▼
  app.main Application (concurrent_updates=True)
        │
        ├─ CommandHandler("*")     → cmd_*  (decorator @logged)
        ├─ CallbackQueryHandler    → on_callback / cb_json
        ├─ MessageHandler DOCUMENT → on_document (PDF)
        ├─ MessageHandler PHOTO    → on_photo
        └─ MessageHandler TEXT     → on_text
                │
                ▼
        @logged / ensure_allowed
                │
        ┌───────┴───────────────────────────────────────────┐
        │                                                   │
   comando com args                              texto livre / pending
        │                                                   │
        ▼                                                   ▼
  _start_tool / serviço dedicado              get_pending(chat_id)?
        │                                         │ yes → finish tool / fluxo
        │                                         │ no  → menu button?
        │                                         │       slug intent?
        │                                         │       PDF context?
        ▼                                         ▼
  start_tool (conversation.py)               reply
        │
        ├─ needs_params e params vazios → set_pending + prompt
        ├─ SCAN_SLUGS → enqueue_scan → "job_id=…"
        └─ senão → run_local / tool_answers / serviço
                │
                ▼
           reply_text (handler)
                │
   [se job RQ]  │
                ▼
           Worker run_scan → send_message(chat_id, relatório)


4.2 Decorator @logged (handlers.py)
-----------------------------------
Para cada comando:
  1) new_request_id + bind_context(user_id, command)
  2) init_db()
  3) ensure_allowed(user.id)
  4) executa handler
  5) captura AccessDenied / RateLimitExceeded / UrlValidationError / AppError
  6) log handler_done com duration_ms e status


4.3 Fluxo texto (on_text) — ordem de decisão
--------------------------------------------
1. Acesso + init_db
2. pending especial (GCP removido, link_learn, ai_sites, text_extract, …)
3. match_menu_button(text) → _handle_menu
4. pending vuln_report / grok_prompt / ai_sites / link_learn / tutor / text_extract
5. is_awaiting (PDF a processar) → lembrete
6. texto começa com / → resolve_slug + _start_tool  (ou PDF context)
7. palavras soltas status/jobs/tools/… → comandos
8. senão → handle_text (conversation: pending genérico, PDF Q&A, Claude bridge)


4.4 Fluxo callback (on_callback)
--------------------------------
answer() imediato → ramo por prefixo de data:
  json_ / grok / ai_sites / link_learn / config / tv / pdf / lovable /
  paginação p:N / tool t:INDEX → _start_tool


4.5 Fluxo scan (detalhado)
--------------------------
User: /scan https://exemplo.com
  → cmd_scan → validação NormalizedUrl (anti-SSRF)
  → rate_limit user + target cooldown
  → create_job(SQLite) status=queued
  → RQ enqueue run_scan(job_id)
  → reply "job sXXXX …"
Worker:
  → mark running → run_passive_scan(url)
  → DNS A/AAAA, TLS cert, HEAD/GET headers (httpx + tenacity)
  → format_scan_report → mark done → send_message(chat)
  → em falha: mark failed + mensagem segura (sem stack ao user)


4.6 Pending Redis
-----------------
Quando a tool precisa de parâmetros e o user não enviou:
  set_pending(chat_id, {tool, user_id, missing, started})
Próxima mensagem de texto completa o pedido (finish_tool) ou /stop limpa.


4.7 Documentos e fotos
----------------------
on_document: PDF → extrai texto → guarda contexto por chat (/pdf limpar)
on_photo: caminhos auxiliares (ex. cam_snap / fluxos que aceitam imagem)


4.8 Worker → Telegram (fora do Application)
-------------------------------------------
adapters/telegram.py usa httpx síncrono:
  sendMessage / sendDocument
Não partilha o loop asyncio do bot — adequado ao processo RQ.

6. OPERAÇÃO RÁPIDA
================================================================================

Status:
  systemctl status bot.service
  systemctl status  # worker unit se existir; senão: ps aux | grep app.worker
  journalctl -u bot.service -f

Reinício bot:
  systemctl restart bot.service

Webhook Conflict (polling surdo):
  curl -X POST "https://api.telegram.org/bot$TOKEN/deleteWebhook"
  systemctl restart bot.service

Enviar ficheiro via CLI Hermes (integração usada nesta doc):
  hermes send --to telegram:7583853645 "MEDIA:/root/bit/doc_bot_hot.txt"


================================================================================
7. LIMITAÇÕES / CONTRATO DE SEGURANÇA
================================================================================

- Scan é passivo: DNS, TLS, headers, GET/HEAD. Sem exploração.
- Anti-SSRF: bloqueia localhost, link-local, metadata cloud, file://
- Rate limit por user/hora e cooldown por host
- Bot privado por allowlist (salvo BOT_PUBLIC=true)
- Export admin não inclui .env, tokens, DB completa com segredos
- Mesmo token Telegram não pode ter Hermes gateway + Bit polling ao mesmo tempo
